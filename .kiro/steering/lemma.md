# Lemma MCP — When to use it

The MCP server `lemma` is connected. What it does that your native tools can't is
**remember across sessions**: the Brain keeps verified fixes and decisions and flags them when
the code they depend on changes. That only pays off if it is consulted and fed, so the moments
below are not optional for MCP-native clients (Claude Code, Cursor, Codex, Windsurf, Kiro,
OpenCode).

> **Muse Code:** you DO NOT have native `mcp__lemma__*` tools. At session
> start, load the `lemma` skill (user scope if present, else
> `.agents/skills/lemma/SKILL.md`) and follow it instead of this file — it
> has priority and uses `lemma call` via bash. Then call `search_memory`
> with the task topic before reasoning. Do not enforce the table below as a
> hard block; use `lemma call` when it actually helps. If no `lemma` skill
> is installed, tell the user to run `npx @nxuss/lemma init`.

## Triggers — always do these

| When… | Call | Why native isn't enough |
|---|---|---|
| Session start | `get_project_onboarding`, then `search_memory` with the task topic | The Brain may already hold the answer |
| Investigating a bug, an error, or a "why does X" | `search_memory` with the error text or question | grep can't find what was learned in another session |
| A 🧠 Lemma note names memories | `get_memory` on the top one | The note carries the headline; the body has the files and the reason |
| A fix is verified (tests pass, build ok, user confirmed) | `store_memory` with `filePaths`: the root cause, the trap or what didn't work — not a summary of what changed | Unsaved, the next session investigates it from scratch; a change summary is already in git log and nobody searches for it |
| You end a session with work half done or split in parts | `store_memory` (or `update_memory` if one exists): what is DONE, what is PENDING, and the exact names/signatures that were specified — don't summarise the spec | The next session starts with no memory of the plan; a vague note loses the details |
| A memory turned out outdated or wrong | `update_memory` / `forget_memory` | A near-duplicate leaves two versions and search mixes them |
| Reading code you haven't located yet, or that may hold secrets | `search_workspace` / `read_workspace_file` | They mask API keys before they reach your context |
| Applying a generated patch | `validate_patch_sandbox` first | Validate before writing, not after |

Outside those moments, use judgment: for a small file you already located, a native read costs
less than the round-trip, and for processes, ports or git Lemma has nothing to add.

## Bug Reporting

1. Call `search_memory` with the error message
2. Call `get_telepathic_hints` (via `lemma_toolbox`) with the relevant file

> Muse: use `lemma call <tool>` (or `node ./lemma-proxy.cjs call <tool>` in this repo — see `.agents/skills/lemma/SKILL.md`).

## One hard rule

Any answer that depends on a cache hit, an auto-suggested fix, or a file compressed for your own
context must be delivered with the real information and without hiding where it came from.
